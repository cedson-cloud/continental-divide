# Continental Divide — Tasks

Working roadmap for the build. Keep this clean: it travels with the repo, and the repo is going public.

## Done

- Core build (steps 1–6): intake → validate → approve → publish, with the append-only audit log. Committed and verified end-to-end against the real Anthropic API.
- PII handling changed from auto-reject to flagged-and-gated (approval requires acknowledgment, recorded in the audit log).
- Status enum on the lifecycle: `pending_approval` → `approved` → `published`, or → `rejected`.
- Submitter name and team added to the request model.
- Notion publisher: `app/notion_publisher.py` pushes pending requests one-way to the Notion approval board, with the submitter/team/call-type/side intake fields and a guard that skips empty selects. Mocked unit tests, no network in the suite.
- Pytest suite and CI across rules, governance, vetting, pipeline, API, and Notion mapping. GitHub Actions runs the backend tests and the frontend build on every push. MIT LICENSE; database renamed to `continental_divide.db`.
- **Plan-scope vetting** (`app/vet.py`): audits an existing third-party tracking plan by reusing `event_name_error`, `property_name_error`, and `pii_hit` from `rules.py` rather than reimplementing them. Adds checks that only make sense across a whole plan — structure, exact and near duplicates (complete linkage), category notes — and emits engine-computed summary counts. `evaluate()` is deliberately not used: its category and duplicate checks test membership in our sample plan, which is wrong for auditing someone else's.
- **Governance as configuration** (`governance/`): YAML profiles with `extends` inheritance, cycle detection, and load-time validation. Two event-naming conventions (`title_case_object_action`, `snake_case_object_action`), templates for Segment and PostHog, and `active.yaml` selecting the enforced profile. `rules.py` gained keyword-only parameters defaulting to its existing constants, so the intake path was unchanged.
- **Tracking-plan vetting agent** (`.claude/agents/tracking-plan-vetter.md`): normalizes a foreign plan, runs the vetting CLI under the active profile, and reports engine verdicts separately from model judgment (rename suggestions, and semantic duplicates the lexical clustering cannot catch).
- **The drafting prompt derives from the active governance profile.** `build_system_prompt(profile)` replaces the hardcoded convention prose, categories come from the profile, and the examples block is engine-generated by running `EXAMPLE_EVENT_NAMES` through `event_name_error()` under the profile's own rules. The natural-language path now enforces the same profile the engine does, and the audit log records which profile both used.
- **Business value captured at intake and reaching the model.** Two live probes measured its effect: it moves the second sentence of the description and nothing else. The remaining lever — letting it propose properties — is tracked separately below.
- **Semantic duplicate review** (`app/catalog.py`): all 28 sample-plan events carry verbatim Segment V2 descriptions, and one model call asks whether a drafted event *means* the same as an existing one. Advisory only — it can never reject a request, a failure inside it never blocks intake, and the model-free paths skip it entirely with no call and no audit entry.
- **The requester confirms before a draft enters the approval queue.** A non-rejected model-path request stops at `draft` and joins the queue only on `POST /requests/{id}/submit`. The Notion push moved from routing to submission. Dismissing a possible duplicate requires a written reason, so a dismissal is a governance record rather than a checkbox. `draft` is a status string; no value was added to the `Decision` enum.
- **The review reports what it found, not only duplicates.** `ReviewFinding.kind` is `duplicate_event`, `property_extension`, or `property_already_exists`, and the question asked depends on the request kind. A `new_property_on_existing` request can never have its own named event reported as a duplicate: the prompt forbids it and `_apply_kind_rules` enforces it deterministically, so the guarantee does not rest on model behaviour.
- **The requester stops landing on the approver's screen.** `AgentReview` replaces `DuplicateReview`, the paragraph explaining engine facts versus model inference is gone, and the request detail page is status-aware — a draft shows the requester their own request with a submit button and no decision panel, publish cards, or audit timeline.
- **The deterministic rule knows what a property request is.** `evaluate()` takes keyword-only `request_kind` and `existing_event`. A `new_property_on_existing` request whose drafted name matches the event it names is expected rather than a duplicate; a match against any *other* event still flags. The exemption lives in `rules.py`, so it holds on every path, not only the ones that call the model.
- **A property-extension finding can be accepted, and accepting it supersedes rather than mutates.** `POST /requests/{id}/convert` drafts a new `new_property_on_existing` request from the original's intake, gives it its own rules pass and its own catalog review, lands it at `draft` for its own confirmation, and only then marks the original `superseded` — with paired `superseded_by` / `supersedes` audit entries so the trail is navigable from either end. A model failure during conversion leaves the original at `draft` so the conversion can be retried. A converted request is the first one that costs four model calls end to end, which is why `/convert` shares the intake rate limiter.
- **Eval harness, deterministic tier** (`backend/evals/`): a committed YAML fixture set where each entry pins one engine decision and carries a note naming it. 14 event-name fixtures and 15 full-definition fixtures, loaded by `backend/tests/test_evals_deterministic.py`, so the tier runs under `pytest` in CI at zero API spend — nothing under `backend/evals/` imports `anthropic` or reads a key. Expectations are three-state: a field left unset is *unscored*, recorded but never failed, and `failed_rules` compares as a set of rule names rather than the prose `detail` strings, which churn. Fixtures pin a governance template explicitly and `resolve_profile()` raises on `active.yaml`, so flipping the active profile cannot silently rewrite every expectation. The value over the existing suite is that a fixture is addressable by claim: a green suite says nothing broke, a fixture says a specific claim is false — which is what the `Newsletter Signed Up` episode needed and the frozen canary could not provide.
