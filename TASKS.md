# Continental Divide — Tasks

Working roadmap for the build. Keep this clean: it travels with the repo, and the repo is going public.

## Done

- Core build (steps 1–6): intake → validate → approve → publish, with the append-only audit log. Committed and verified end-to-end against the real Anthropic API.
- PII handling changed from auto-reject to flagged-and-gated (approval requires acknowledgment, recorded in the audit log).
- Status enum on the lifecycle: `pending_approval` → `approved` → `published`, or → `rejected`.
- Submitter name and team added to the request model.
- Notion publisher: `app/notion_publisher.py` pushes pending requests one-way to the Notion approval board, with the submitter/team/call-type/side intake fields and a guard that skips empty selects. Mocked unit tests, no network in the suite.
- Pytest suite and CI across rules, governance, vetting, pipeline, API, and Notion mapping. GitHub Actions runs the backend tests and the frontend build on every push. MIT LICENSE; database renamed to `continental_divide.db`.
- **Plan-scope vetting** (`app/vet.py`): audits an existing third-party tracking plan by reusing `event_name_error`, `property_name_error`, and `pii_hit` from `rules.py` rather than reimplementing them. Adds checks that only make sense across a whole plan — structure, exact and near duplicates (complete linkage), category notes — and emits engine-computed summary counts. `evaluate()` is deliberately not used: its category and duplicate checks test membership in our sample plan, which is wrong for auditing someone else's.
- **Governance as configuration** (`governance/`): YAML profiles with `extends` inheritance, cycle detection, and load-time validation. Two event-naming conventions (`title_case_object_action`, `snake_case_object_action`), templates for Segment and PostHog, and `active.yaml` selecting the enforced profile. `rules.py` gained keyword-only parameters defaulting to its existing constants, so the intake path was unchanged.
- **Tracking-plan vetting agent** (`.claude/agents/tracking-plan-vetter.md`): normalizes a foreign plan, runs the vetting CLI under the active profile, and reports engine verdicts separately from model judgment (rename suggestions, and semantic duplicates the lexical clustering cannot catch).
- **The drafting prompt derives from the active governance profile.** `build_system_prompt(profile)` replaces the hardcoded convention prose, categories come from the profile, and the examples block is engine-generated by running `EXAMPLE_EVENT_NAMES` through `event_name_error()` under the profile's own rules. The natural-language path now enforces the same profile the engine does, and the audit log records which profile both used.
- **Business value captured at intake and reaching the model.** Two live probes measured its effect: it moves the second sentence of the description and nothing else. The remaining lever — letting it propose properties — is tracked separately below.
- **Semantic duplicate review** (`app/catalog.py`): all 28 sample-plan events carry verbatim Segment V2 descriptions, and one model call asks whether a drafted event *means* the same as an existing one. Advisory only — it can never reject a request, a failure inside it never blocks intake, and the model-free paths skip it entirely with no call and no audit entry.
- **The requester confirms before a draft enters the approval queue.** A non-rejected model-path request stops at `draft` and joins the queue only on `POST /requests/{id}/submit`. The Notion push moved from routing to submission. Dismissing a possible duplicate requires a written reason, so a dismissal is a governance record rather than a checkbox. `draft` is a status string; no value was added to the `Decision` enum.
- **The review reports what it found, not only duplicates.** `ReviewFinding.kind` is `duplicate_event`, `property_extension`, or `property_already_exists`, and the question asked depends on the request kind. A `new_property_on_existing` request can never have its own named event reported as a duplicate: the prompt forbids it and `_apply_kind_rules` enforces it deterministically, so the guarantee does not rest on model behaviour.
- **The requester stops landing on the approver's screen.** `AgentReview` replaces `DuplicateReview`, the paragraph explaining engine facts versus model inference is gone, and the request detail page is status-aware — a draft shows the requester their own request with a submit button and no decision panel, publish cards, or audit timeline.
- **The deterministic rule knows what a property request is.** `evaluate()` takes keyword-only `request_kind` and `existing_event`. A `new_property_on_existing` request whose drafted name matches the event it names is expected rather than a duplicate; a match against any *other* event still flags. The exemption lives in `rules.py`, so it holds on every path, not only the ones that call the model.
- **A property-extension finding can be accepted, and accepting it supersedes rather than mutates.** `POST /requests/{id}/convert` drafts a new `new_property_on_existing` request from the original's intake, gives it its own rules pass and its own catalog review, lands it at `draft` for its own confirmation, and only then marks the original `superseded` — with paired `superseded_by` / `supersedes` audit entries so the trail is navigable from either end. A model failure during conversion leaves the original at `draft` so the conversion can be retried. A converted request is the first one that costs four model calls end to end, which is why `/convert` shares the intake rate limiter.
- **Eval harness, deterministic tier** (`backend/evals/`): a committed YAML fixture set where each entry pins one engine decision and carries a note naming it. 14 event-name fixtures and 15 full-definition fixtures, loaded by `backend/tests/test_evals_deterministic.py`, so the tier runs under `pytest` in CI at zero API spend — nothing under `backend/evals/` imports `anthropic` or reads a key. Expectations are three-state: a field left unset is *unscored*, recorded but never failed, and `failed_rules` compares as a set of rule names rather than the prose `detail` strings, which churn. Fixtures pin a governance template explicitly and `resolve_profile()` raises on `active.yaml`, so flipping the active profile cannot silently rewrite every expectation. The value over the existing suite is that a fixture is addressable by claim: a green suite says nothing broke, a fixture says a specific claim is false — which is what the `Newsletter Signed Up` episode needed and the frozen canary could not provide.

## Next

- [ ] **Eval harness, live tier.** The deterministic tier guards the engine; this one guards the model. Reuse `live_ab.py`'s execution path (`interpret` → `model_validate` → `evaluate`), its per-run text summary, and its label filter; rebuild the rest — it has no expectations, its comparison diffs two probes *within* one run rather than one fixture *across* runs, and it never calls `review_against_catalog`, so whether the semantic review fires on a case it should is still unmeasured. Score name shape, dictated names verbatim, category, property-name sets, decision, failed-rule names, and the `(kind, existing_event)` pairs the review returns. Record and diff the drafted description; never score it — it is the only field with no closed vocabulary. Results append to gitignored JSONL with a committed `baseline.json` of scores and digests only, never raw model prose, which would otherwise land permanently in the history of a public repo. Provenance per line: digests of the *rendered* system prompts (they derive from the profile, so one hash catches both a YAML change and a code change to the builder), the profile, the model id, `git_head`, and a fixture digest. ~$0.018 per fixture, ~$0.21 per 12-fixture run. Out of CI; `--live` required to spend, and a hard `--max-calls` that prints every fixture it skipped.
- [ ] **Eval fixture ids are unique per list, not globally.** `posthog_clean` and `posthog_rejects_title` each appear under both `names:` and `definitions:`. Harmless for pytest node ids, but the live tier keys its JSONL results on fixture id, so a cross-run delta would silently join two different fixtures. Rename before the delta printer exists.
- [ ] **`duplicate` appears as a `RuleCheck` only on the exemption branch.** A genuine duplicate is flagged with no check explaining it, which is backwards. The fix is to always emit the check — passing when the name is novel or exempted, failing when the duplicate is real. `test_rules.py:114` asserts `all(c.passed ...)`, so the frozen canary is the right instrument: if it fails, the change is wrong. Pinned by the `duplicate_check_absent` eval fixture, which ships as a `strict=True` xfail carrying this item as its reason — CI stays green today, and the marker becomes a hard failure the day the check is always emitted, forcing its removal.
- [ ] **No frontend tests exist.** The largest UI change in the project shipped with `tsc --noEmit` and one backend test as its entire verification surface. Not full coverage — `AgentReview` across the three finding kinds, both variants, and the empty case, plus the draft-versus-approver branch on the detail page. Vitest + React Testing Library, one dev dependency, matching the existing unit-test posture; Playwright is the alternative and belongs later, once there is a full intake → confirm → approve flow worth driving end to end.
- [ ] **`/requests/raw` no longer pushes to Notion.** A consequence of moving the push from routing to submission: the raw path skips `draft`, so it never passes through `submit_request`. A raw request still reaches the approval queue, so the board goes silently incomplete. Restore the push on that path, and handle demo-run pollution separately.
- [ ] **`run_examples.py` publishes to the live Notion approval board when `NOTION_TOKEN` is set.** One page per example, on every run.
- [ ] **`decide()`'s gate is findings-aware, its exception class is not.** The field, the message, and the audit entry are all `findings_acknowledged` and name the kinds actually stored; the internal exception is still `DuplicateAcknowledgmentRequired`. Not user-facing, but a stranger reading the module will notice.
- [ ] **Publish failure handling.** On the approve path, a publisher error should record a `publish_failed` audit entry instead of stranding the request at `approved`.
- [ ] **Concurrent-decision guard.** Add a compare-and-swap on status so a request can't be decided twice concurrently.
- [ ] **Harden `POST /requests/raw`.** Apply the rate limit and a size cap, as the model-backed intake route already does.
- [ ] **Guided rename-and-resubmit.** A naming failure should offer the compliant name and a one-click resubmit, with consent recorded in the audit trail, instead of a terminal rejection before a human ever sees it.
- [ ] **"Not sure" on client vs. server.** Route the question to the approver rather than forcing a guess at intake.
- [ ] **Support identify, page, and screen calls.** EventDefinition is track-shaped and rules.py enforces a track event-naming convention; traits and page calls need their own shapes and their own rules. The intake UI was narrowed to track rather than advertise support that does not exist.
- [ ] **`EXAMPLE_EVENT_NAMES` is tuned for Title Case.** Under `posthog-snake-case.yaml` the prompt renders 2 PASS and 7 FAIL, five carrying the identical message "name must be lowercase snake_case (object_action)". Thin, repetitive few-shot material. Fix by growing the example list so both conventions get a real spread — not by hand-writing verdicts.
- [ ] **`interpret(profile=None)` calls `load_active_profile()` unguarded.** A third bare call site, same class as the guarded/bare split already fixed once. The API path is safe because `routes.py` resolves through `_active_profile()` first; a direct caller with a malformed `active.yaml` is not.
- [ ] **No governance template declares categories.** Both templates hit the sample-plan fallback, so the profile-categories path is proven only by an in-memory test and is invisible on `/admin` and in any demo.
- [ ] **`source: requested | suggested` on `EventProperty`.** A drafted event carries only the properties the requester named — `product_id` and nothing else — which joins to very little. The catalog and the platform spec could propose the rest, but only if the field records what was asked for versus what was suggested. Without that distinction the model is designing the plan rather than capturing the request, which is the thing this architecture exists to prevent.

## Later

- [ ] **Admin view of the active profile.** Read-only display of the enforced rules and their history. Rules live in git, so `git log` supplies the history at no cost.
- [ ] **Setup flow that authors a profile.** Pick a template, then override, from a curated list of known conventions — never free-form regex.
- [ ] **Re-vet on rule change.** When a profile changes, report which existing events no longer comply.
- [ ] **Platform specs as data** (`platforms/*.yaml`): call shape, identity model, and source URL for Segment, PostHog, and Hightouch. The three SDKs differ structurally, not cosmetically, so one template with a swapped function name will not work. The app, the agent, and any skill must read one file or they will drift.
- [ ] **Code snippets per SDK**, generated from those specs and syntax-checked in CI. A wrong snippet is worse than no snippet, because it gets shipped.
- [ ] **Categories in one place.** `evaluate()` reads them from `sample_tracking_plan.json`; `vet.py` reads them from the profile. The sample plan is a fixture and should not also be configuration.
- [ ] **Configurable catalog source for the duplicate review.** `catalog_entries()` reads the bundled sample plan; in a real deployment the catalog would come from the customer's own tracking plan, so the source should be configurable the way governance profiles are.
- [ ] **`pii.mode: block`.** Reserved in the schema, not implemented.
- [ ] **Notion board categories drift from the sample plan.** Notion auto-creates missing options, so nothing breaks, but the demo looks inconsistent.
- [ ] **Notion board has no properties for the newer intake fields.** Business value, request kind, and existing event are captured at intake and never reach the board.
- [ ] **`urgent`, `urgency_reason`, and the date-typed `needed_by` join that list** of intake fields the Notion board has no properties for.
- [ ] **`properties` as a non-list is silently skipped** in `vet.py`, and the event then reports that all property names are snake_case — a passing check on properties nobody examined.
- [ ] **`StarletteDeprecationWarning`** on `httpx` with `starlette.testclient`.
